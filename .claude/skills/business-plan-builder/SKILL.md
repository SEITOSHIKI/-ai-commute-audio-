# 事業計画の立案・作成

事業のアイデアを「数字に根拠がある計画」と「人に伝わる資料」にするスキル。中身は、ある研修課題（AIグラス×電気工事の事業「カンツギ」）で、本人と何十回もやり取りして固まった進め方をまとめたもの。そのときの指摘を、最初から守れるようにしてある。

## 成果物（標準セット）

| 成果物 | 中身 | 使う場面 |
|---|---|---|
| 計算モデル（1ファイル） | 前提・式・5年と10年の収支・崩れたとき・撤退ライン | すべての数字の出どころ |
| 本編（25〜35枚） | 課題の設問の順に、結論と一行の式 | 一番詳しい発表版 |
| 計算詳細版（質問用） | 本編の数字の計算過程と前提・出典 | 質問されたら開く |
| 16枚版 | 本編を16枚に統合。A4用紙2枚（表裏4ページ・1ページ4枚）と10分に収める | 提出・配布・本番 |
| やさしい版（マンガ） | 数字に慣れていない人向けに同じ数字を絵で | 一般の聞き手 |
| サービス説明資料（12枚前後） | お客様の立場ごと（現場の方・経営の方）の実利・使う場面・導入の進め方 | 説明会・商談・発表の補足 |
| 裏取りのExcel（とPDF） | 計算詳細版の数字を、前提のセルを参照する式でたどれるようにしたもの。計算モデルの値と照合する列つき | 数字の確認・質疑 |
| 台本（md と 台本つきPDF） | 本人の言葉で、1分約300字 | 練習・本番 |
| 想定問答（md） | 厳しい質問への一言の答えと根拠ページ | 質疑 |
| note記事の種 | 事業計画から記事の企画を出す | 発信 |

全部が毎回いるわけではない。最初に何が要るかを聞いて決める（下の「0. 前提の確認」）。

## 進め方

各段階の終わりで、本人に短く報告して次へ進む。数字を固める前に、前提を本人と合わせる。

### 0. 前提の確認
`references/interview.md` の質問を使って、次を最初に決める。後から変わると全資料を作り直すことになるので、ここは手を抜かない。
- 課題の設問（例：①事業・理由・想い ②スタッフ ③経営理念 ④年単位の計画と収支 ⑤段階ごとの課題）。資料はこの順番に並べる
- 発表時間と枚数、印刷の形（例：10分・16枚・A4用紙2枚の表裏）
- 資金の前提（自己資金か、融資・出資か）。研修なら「豊富な資金」など課題の前提に合わせる
- 個人情報（発表者名を載せるか）。載せないなら表紙・台本・ファイル・コミットメッセージのどこにも書かない
- 本人の経歴のうち、資料に使ってよいもの

### 1. 構想
事業を一文で言う。誰の・どんな困りごとを・どう解くか。選んだ理由は「市場・技術・自分」の3つで整理し、本人の経験と必ずつなげる。

### 2. 調査
一次情報（統計の原表・公的資料・各社の公表資料）を優先し、出典を残す。特に次の2つは毎回やる。
- **同じ方向の大手を探す**。「人が入力するアプリ」だけを競合にしない。大手がすでに似たことをしていたら、隠さずに比べて、領域をずらす（例：日立グループの保守・安全に対して、中堅の施工・書類に絞った）
- **大手の稼ぎ方を調べる**。AIそのものを売っているのか、既存の契約に組み込んでいるのかで、真似できる部分が変わる

### 3. 計算モデル
`references/model_guide.md` を読んでから、`assets/model_template.js` をコピーして1ファイルにつくる。資料の数字はすべてここから出し、手で書き換えない。要点は次のとおり。
- お客様の効果は「使う人の分だけ」数える。全社員が得をする計算にしない
- 時給は「統計の年収 × 会社負担（約1.17）÷ 残業込みの年間総実労働時間」。所定の時間で割らない
- 確度を「統計・公表・見積・仮説」の4つに分けて表にする。仮説は実証で測るものとして扱う
- 黒字になる値を逆算しない。赤字ならそのまま出し、黒字化の条件（例：1拠点の台数）を別に示す
- 5年で終わらせず、10年まで同じ式で延ばす。ストレステスト（値下げ・解約・原価2倍・採用の遅れ）と撤退ラインもつくる

### 4. 実現可能性の見直し
`references/review_checklist.md` で、計画の弱いところを自分から指摘する。本人は「弱みを先に言う」計画を好む。見つけた弱点は資料に「弱いところ」として載せ、確かめ方とセットにする。

### 5. 資料
`references/deck_guide.md` を読む。二段構え（本編＝結論と一行の式、計算詳細版＝計算の過程）にし、本編の右上に「計算の詳細：詳細版 p.○」を入れる。16枚版は本編の2〜3枚を1枚に統合し、式・表・前提は削らない（削ると「浅い」と言われる）。

### 6. デザイン
`assets/theme_drawing.js` を使う。図面の外枠と右下の表題欄、紺の見出しと表、安全色（進む＝緑・注意＝黄・止まる＝赤）、BIZ UDPゴシック。黒い箱・ベージュの差し色・細い罫線・グレーの小さな注記の組み合わせは、AIが作った資料に見えるので避ける。

### 7. 台本と言葉選び
`references/voice_guide.md` を読む。結論を先に、論点に番号、数字で語る、本人の経験とつなげる、用語をそろえる。飾った言い回しは置換表で直す。締めは「ご清聴ありがとうございました」。速さは1分約300字で時間を出し、10分なら台本は約9分半にして残りを間にする。

### 8. 仕上げ
1. pptx を検証し、PDFに変換して画像で全ページを目で確認する（文字のはみ出し・重なり・見出しの折り返し）
2. 台本つきPDF：`scripts/notes_html.py` → `scripts/html_pdf.js`。台本のmdは `scripts/notes_md.py <pptx> <md>` でノートから作り直す（手で直さない）
3. 配布用PDF：`scripts/handout.py <画像フォルダ> out.html "題名" 4`（A4横・1ページ4枚、両面は短辺とじ）または `8`（A4縦・1ページ8枚）
4. `scripts/check_names.py <フォルダ> --names-file <名前の一覧> --git` で、載せない名前がファイルとコミットメッセージに残っていないかを調べる（名前の一覧はリポジトリの外に置く）。過去のコミットに残っていたら、履歴を書き換えるかを本人に確かめる
5. 一式を zip にまとめる

## note記事への展開

本人は note（ペンネーム）で記事を書いている。事業計画ができたら、`references/note_bridge.md` に沿って記事の種をつくり、note-article-generator スキルに渡す。`scripts/make_note_seeds.py` が、計算モデルの要約（plan_summary.json）から記事の企画（topics.yaml と素材md）を出す。職歴と結びつく内容は、公開前にペンネームの匿名性を確かめる。

## エージェントとの分担

| エージェント | 役割 |
|---|---|
| `business-planner`（`.claude/agents/business-planner.md`） | このスキルで事業計画を一式つくる。別の事業案を並行して検討するときに、案ごとに1つずつ動かす |
| `bizplan-note-bridge`（`.claude/agents/bizplan-note-bridge.md`） | できた事業計画から記事の種をつくり、note-article-generator で下書きを書く。記事で出た切り口を次の事業計画に戻す |
